# HDR-9000 Design

## Goal

Add HDR-9000 as a second, independent device workflow. It indexes only stable
XML files whose trimmed `Product_Model` is exactly `HDR-9000`, immediately
processes each distinct file revision, and sends a sparse HIS update without
changing the KR-800 pairing workflow.

## Boundaries

- KR-800 modules, pair tables, statuses, event names, and runtime state retain
  their existing behavior.
- HDR-9000 has its own parser, watcher loop, process state, queue, events, and
  persistence tables. It may reuse app configuration, authentication/token
  refresh, HTTP retry conventions, app logging/redaction, and generic folder
  commands.
- HDR-9000 never reads the KR-800 refraction catalog and never creates a
  measurement pair.

## Persistence

The existing `device_config` row keyed by `hdr-9000` stores its tracking
folder and auto-process setting.

New forward-only, idempotent tables are dedicated to HDR-9000:

- `hdr9000_revisions`: one row per `file_path + content_hash`; stores filename,
  `ma_ho_so` (filename stem), XML `Patient_ID`, filter date and its source,
  source time, immutable parsed sparse payload snapshot, service ID cache used
  for the send, persisted request/response, lease/retry metadata, and status.
- `hdr9000_field_versions`: one row for every successfully-sent HIS field,
  keyed by `ma_ho_so + field_path`. It records the source time and revision ID
  that last won that field. A later successful revision supersedes only fields
  it contains.
- `hdr9000_service_cache`: service-visit ID keyed by `ma_ho_so`, reused for
  later revisions. An invalid-service response deletes this cache and causes
  one resolution retry.

Revisions retain historical audit rows. A unique index on `(file_path,
content_hash)` makes same-content rediscovery idempotent while allowing an
overwritten path with a new hash to be queued as a new revision.

## Indexing and dates

All scans and watcher events wait for file stability. The tracker reads the
bytes at indexing time, validates XML and product model, computes SHA-256, and
stores the snapshot so later file overwrites cannot alter queued work.

Filter date uses filesystem creation time, then a valid eight-digit
`Measurement_Date`, then filesystem modified time, then discovery time. The
stored `date_source` makes this auditable. Source ordering uses creation time,
then modification time, then discovery time, with database revision ID as the
tie-breaker. `Measurement_Date` is never used to infer first versus second
measurement.

Non-HDR XML is not indexed or queued. The tracker logs its model/file/hash
summary and increments its skipped count. The processor validates the model
again before sending.

## Parsing and HIS payload

The HDR parser reads only `Final_Prescription_Data` tags. It uses filename stem
as `maHoSo`, retaining `Patient_ID` only for reconciliation. Numeric SPH, CYL,
Axis, VA, and ADD values are sent directly; PD values preserve their XML string
representation. Empty, missing, or invalid values do not yield a field.

Payload construction is JSON-object based and sparse at every level. An empty
eye object is omitted. The mappings are:

- FAR right/left SPH, CYL, Axis, VA map to `matPhaiKinhMoi` /
  `matTraiKinhMoi` fields.
- FAR ADD maps to `matPhaiCapKinhNhinGan` /
  `matTraiCapKinhNhinGan.donViAddId`.
- Optional NEAR right/left data maps to the respective near-glasses object.
- `Far_PD_OU` and `Near_PD_OU` map to `dongTuXa` and `dongTuGan`.

No nulls, implicit zeroes, catalog IDs, or unrelated XML sections are sent.

## Processing and recovery

A separate HDR runtime state owns a run lock, token lock, and per-record locks.
Processing is serialized per `hdr-9000 + maHoSo`. Before every initial send or
retry, the worker compares each requested field with `hdr9000_field_versions`.
Fields already sent successfully by a newer revision are removed. If none
remain, the revision becomes `superseded` without a HIS request.

For remaining fields, the worker resolves the patient/treatment using the
existing HIS APIs, selects `dsDvKham[0].id`, and saves/reuses the HDR service
cache. It persists the exact sparse request and response. Normal transient,
authentication, lease-expiry, and startup recovery behavior follows the
existing application's conventions.

## UI and events

HomeShell gains an HDR-9000 sidebar item and a dedicated `Hdr9000Panel`. The
panel mirrors KR-800 operational controls: folder selection, rescan, date
filter, file list/status, manual processing, auto-process, progress, and
errors. Its React state is local to the panel and keyed to `hdr-9000`.

Events use only `hdr9000:*`: scan progress, files indexed, file progress,
watch status, and auto-process. The backend exposes `process_hdr9000`; existing
generic folder, rescan, list, and auto-process commands continue accepting
`deviceKey`.

## Tests and verification

Backend unit tests cover model validation, parsing and sparse serialization,
date fallbacks, revision/idempotency rules, cached service ID reuse, and stale
retry field filtering. Existing KR-800 tests remain unchanged. Local
verification runs `git diff --check` and the frontend typecheck/build only;
Cargo/Rust installation, Cargo test/check/clippy, and Tauri build are excluded.
